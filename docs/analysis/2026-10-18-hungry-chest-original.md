## Inventory, collection, and automation contracts

- **27 usable slots, not 36:** `TileChestHungry:24–35` implements ordinary `IInventory`, initially allocates 36 backing entries, but reports 27. `:74–96` reloads into exactly 27 entries; save loops backing-array length. GUI, insertion, comparator, and break drops use the reported size. Entries 27–35 are not extra gameplay storage; fresh-world native storage should have 27 slots, not reproduce inaccessible transient backing entries or promise old-world migration.
- **Inventory limit 64:** `TileChestHungry:62–68,99–105,175–177` setter clamps only to 64, accepts every item, and usability requires this exact tile plus squared distance at most 64. `:41–60` splits/removes native stacks. No slot filter, face restriction, owner lock, fuel, or player research check is attached to inventory access.
- **Insertion order is two-pass:** `InventoryUtils:49–60` copies the incoming entity stack; `:79–103` first visits occupied item/damage-matching slots **0→26**, then visits **0→26** again for insertion into empties/remaining matches. `getDoubleChest:458–473` only recognizes vanilla `TileEntityChest`, which this tile is not. A later matching stack must be merged before an earlier empty slot is used; this is not simply one forward vanilla-hopper insertion pass.
- **Exact merge identity/cap:** `InventoryUtils:124–158,279–280,313–340` requires same item, damage/metadata, and full NBT equality; count is not part of equality. Positive merge room is `min(64 - existingCount, incomingItemMax - existingCount)`. Native equivalent must use full `ItemStack.isSameItemSameComponents`, not item-only, tag-only, or selected-component equality. Names, damage, enchantments, container contents, and TC components must survive both merge and residual paths.
- **Empty-slot quirk:** `InventoryUtils:128–140` takes up to **inventory limit 64**, without consulting item maximum; it can store an anomalous multi-item unstackable/16-limit stack. Do not describe the original as always using `min(64,itemMax)`. Valid ordinary incoming stacks are unaffected. If modern insertion deliberately applies native item/component maximum to empties, label that deviation and retain every excess item in the source entity; never silently clamp/delete its excess.
- **Residuals:** `BlockChestHungry:145–165` inserts server-side only for a live `EntityItem`. Fully accepted → remove entity; partial → replace entity stack with the exact leftover; zero accepted/full/incompatible → retain full source. Eat feedback is conditional on decreased count, not mere contact. The original marks the tile dirty even on a no-progress item contact; that is not permission for eat feedback or viewer events on rejection.
- **No suction:** the collection path is only `BlockChestHungry.func_149670_a` (entity collision callback). `TileChestHungry:111–140` ticks lid animation/sounds only. There is no attraction radius, item scan, velocity steering, or ticker pickup. `BlockChestHungry:153–164` does **not** inspect pickup delay or dropped-item owner/thrower; ordinary delayed/owner-marked drops can be eaten. Those properties are not modern rejection conditions merely because player pickup would reject them.
- **Different physical and selection shapes:** `BlockChestHungry:136–143` physical AABB is `(1/16,0,1/16)→(15/16,15/16,15/16)`; state/selection bounds end at **14/16 Y**. Modern `entityInside` is a block-cell callback, not proof of physical-shape contact. An explicit native contact gate must use the **physical** AABB, include a resting/touching top surface with only numerical boundary tolerance, and not use the lower selection box, whole cell, or a grown pickup radius. Be precise about provenance: the original callback body itself does not perform an AABB intersection test; an explicit shaped-contact gate is the port's boundary adaptation, not a check quoted from that body.
- **Ordinary automation/comparator:** `TileChestHungry:24–26,175–177` is not `ISidedInventory`; all 27 slots are available for ordinary insertion/extraction from every face. The caller's `side=1` in collision insertion does not make a top-only slot policy. `BlockChestHungry:88–98` delegates comparator strength to vanilla inventory fullness. Native plain `Container` is enough; an optional `WorldlyContainer` must expose identical all-face access, not add sided rules.

Concrete normal-stack example: slots 0 empty, 7 containing identical 60, others full; incoming 10 → slot 7 becomes 64, slot 0 becomes 6, entity gone. If slot 0 is also full → slot 7 becomes 64 and entity retains 6. If all 27 slots are already full → incoming 10 stays unchanged and no eat/chomp feedback occurs. These are **expected**, not executed results.

## Placement, opening, lid, sounds, and rendering

- `BlockChestHungry:100–104` uses **piston placement orientation**, with metadata `0=down,1=up,2=north,3=south,4=west,5=east`; the unused local `metadata & 3` does not constrain the stored result. Preserve vertical placements; a horizontal-only state or simple pitch-only approximation is not that determinant. Avoid reproducing the original unnecessary `EntityPlayer` cast crash for nonplayer placement contexts.
- `BlockChestHungry:168–177` directly opens the tile on server interaction. There is **no** above-solid obstruction test, sitting-ocelot/cat rule, adjacent-chest placement restriction, or combined/double inventory. Do not import these by subclassing vanilla chest behavior. The ordinary three-row menu is appropriate; opening does not require `HUNGRYCHEST` research once a chest physically exists.
- `TileChestHungry:70–72,171–173` names the inventory literally `Hungry Chest` and reports no custom inventory name. A native localized title may reproduce that name; custom-name/lock mechanics are not original requirements.
- `TileChestHungry:117–139` preserves previous lid angle, moves current angle by **0.1/tick**, clamps to `[0,1]`; starts `random.chestopen` at angle 0 when viewers >0; emits `random.chestclosed` while crossing below 0.5. Both use volume **0.5**, pitch `randomFloat*.1+.9`. Native chest-open/close sound identifiers are the identifier adaptation.
- `TileChestHungry:142–164` event **1** assigns viewer count, with actual GUI open/close increment/decrement sending that event; event **2** raises lid to at least `parameter/10`. Successful collection sends **(2,2)** and plays `random.eat` at the item entity, volume **0.25**, pitch `(randFloat-randFloat)*.2+1` (`BlockChestHungry:155–157`). It does **not** create an artificial viewer or event 1. Hoppers/menu-independent mutations must not call `startOpen`, `stopOpen`, or increment viewers; hopper transfer itself also sends no chew event2/eat sound. A lone chew opens to 0.2 then shuts without crossing the 0.5 close-sound threshold. Original viewer decrement is unclamped; preventing stale-close underflow is a safety adaptation, not evidence of an original rescan/repair algorithm (`:114–116` is an empty sync branch).
- `TileChestHungryRenderer:28–65` uses vanilla **`ModelChest`**, not a TC-specific OBJ or a double-chest model. Metadata rotations: **0/1→0°, 2→180°, 3→0°, 4→90°, 5→−90°**; vertical placements do not tilt the model. Interpolate lid, apply `1-(1-angle)^3`, then rotate lid by `−angle*π/2`. Keep the old transform/UV layout and latch with the lid; no missing-texture cube is an acceptable visual substitute.
- `BlockChestHungryRenderer:29–42` renders the inventory item in 3D by a fresh closed tile rendered through the TESR, with an extra 90° Y transform; world block mesh returns false because the tile renderer draws it. `O/client/ClientProxy.java:530,594–595` registers the TESR/block render handler. In 1.21 this needs the actual BER plus an actual item/inventory rendering route, not merely a blockstate/JSON shell. The registered `woodplain` icon (`BlockChestHungry:66–74`) is a fallback/particle icon, **not** the chest model texture.

**Asset provenance:** original JAR entry `assets/thaumcraft/textures/models/chesthungry.png` and both currently available `common/src/main/resources/assets/thaumcraft/textures/{models,blocks}/chesthungry.png` have SHA-256 **`2b8dc5862822afa315c2c797e7b8081daa7be89517bdb36c69ff437ee04ac8cb`**. ## Native content fit and narrowly scoped safety adaptations

- **Use the standard 27-slot container/menu and native stack codecs.** 1.21.1 API references checked: [ChestMenu.threeRows(int, Inventory, Container)](https://mappings.dev/1.21.1/net/minecraft/world/inventory/ChestMenu.html), [ContainerHelper.saveAllItems/loadAllItems with HolderLookup.Provider](https://mappings.dev/1.21.1/net/minecraft/world/ContainerHelper.html), and [ItemStack copy/split, full component equality, save/parse](https://mappings.dev/1.21.1/net/minecraft/world/item/ItemStack.html). These carry actual 1.21 stacks/components; there is no content reason for a bespoke GUI packet inventory or a new generic custody framework. Use native menu synchronization for slot data, with lid/viewer events separately. This is API/content-fit assessment, not a compile/runtime result.
- **Do not copy old mutation ordering blindly.** Original collection credits slots (including repeated `markDirty` calls) before replacing/deleting the entity's stack. With modern callback/reentrant notifications, that can expose both source and credited contents. Keep a chest-local in-progress guard, validate live server/current tile/source identity, and publish destination counts and source residual before callback-bearing dirty/comparator/sound/event notifications. Reject stale/client/reentrant/invalid work without consuming or manufacturing items. Preserve components and exact accepted+residual count. Do not retrofit unrelated systems.
- **Guard the malformed-overstack merge case explicitly.** Original `InventoryUtils:142–148` can compute negative room when an existing slot exceeds item maximum, increasing the leftover and decreasing the slot. Native code must not perform a negative transfer: saturate room at zero and keep the source. This is a justified malformed-input safety deviation, distinct from silently changing the ordinary empty-slot 64 quirk. Never truncate an incoming world stack just because it is larger than one destination slot; distribute or retain its remainder.
- **Existing durable removal route fits the content, but not every visual detail.** Read-only `common/src/main/java/thaumcraft/common/blocks/BlockPedestal.java:44–47` and `common/src/main/java/thaumcraft/common/tiles/TilePedestal.java:87–93` enqueue before clearing/notifying rather than spawn from `onRemove`. `common/src/main/java/thaumcraft/common/lib/utils/DeferredItemDrops.java:411–433,457–575` defers delivery to level-post and retains rejected spawns; `:595–705` reads saved pending rows. Reuse this established ordinary route, not Bore work/custody machinery. Clear the physical chest once after successful handoff, before notifications; state/facing changes of the same block must not evacuate it; repeated/reentrant removal must not pay twice. A canceled/unadmitted spawn is retained, not silently lost as in the old unchecked spawn call.
- **Do not claim identical break scatter from plain enqueue.** Original `BlockChestHungry:106–133` uses the block's `Random`, chooses an offset per source slot, splits drops into **10–30-item chunks**, copies NBT, and gives each chunk Gaussian motion (`.05`, Y `+.2`). Ordinary `DeferredItemDrops.enqueue` currently queues each supplied stack whole with a per-entry offset/motion and a fresh evacuation RNG. Count/components and safe delivery fit; exact chunking/coordinate reuse do not. Preserve them locally if required, or explicitly record that bounded visual/drop-segmentation adaptation. Merely pre-splitting and invoking enqueue is still not exact offset reuse.
- **Durable is not power-loss atomicity.** Pending-drop saved data plus ordinary chunk/entity saves is not a transaction across all native files or arbitrary crashes. Do not claim full native save/callback/power-loss exactly-once guarantees from this route or from this review. Fresh native worlds only; no old JAR/save changes or world migration.
