# Нечёткое сравнение предметов голема (Entropy) — контракт оригинала, 19.10.2026

Источник: оригинал TC4 4.2.3.5 (локальная декомпиляция CFR вне репозитория). `E:` — `EntityGolemBase`, `GH:` — `GolemHelper`,
`IU:` — `InventoryUtils`, `IM:` — `InventoryMob`, `GUI:` — `GuiGolem`.

## Три переключателя

- Хранятся в `toggles` сущности (E:785-805): индекс 5 — `checkOreDict()`, 6 — `ignoreDamage()`, 7 — `ignoreNBT()`; в отличие от
  индексов 1–4 (Guard) они **положительные** (бит установлен = включено). Кнопки меню `55 + n` (`ContainerGolem:86`,
  `GUI:376-389`), подписи «Use Ore dictionary» / «Ignore item damage» / «Ignore NBT values».
- Показываются при `Entropy ≥ 1` у ядер `ItemGolemCore.canSort`: **Fill 0, Empty 1, Gather 2, Use 8, Sorting 10**
  (`GUI:214-262`). Позиция: Sorting `(66, 12 + 24 + 10n)`, остальные `(180, 24 + 10n)`.
- Слот цвета Order и переключатели не связаны; оба читают одно и то же сравнение (`getColorsMatching`, E:517-535).

## Сравнение `IU.areItemStacksEqual(a, b, ore, damage, nbt)` (IU:295-323)

1. `null`/`null` → равны; один `null` → нет.
2. `ore`: если у `a` есть **первое** ore-имя и `b` входит в его список — равны (несимметрично; иначе падение на обычное сравнение).
3. Иначе: предмет один и тот же; `nbt` выключен → теги равны (`areItemStackTagsEqual`); повреждение: разные `damage` не равны,
   **кроме** `ignoreDamage` при двух ломающихся стеках или при wildcard-метаданных.

## Где оно применяется

| Ядро | Место | Эффект |
|---|---|---|
| Fill 0 | `GH.getContainersWithGoods` (:133-152), `AIFillTake:48-50` (`extractStack`), `GH.getMissingItems` (:186-196) | поиск источника, **забирается предмет слота** (не образец), подсчёт имеющегося в домашнем хранилище |
| Empty 1, Use 8 | `GH.getItemsNeeded` (:432-448) → `IM.getItemsNeeded(Entropy>0)` (:236-277), `AIHomeTake:53`, `AIHomeReplace:56` | при Entropy образцы **расширяются всеми предметами первого ore-имени** образца — независимо от переключателей; затем `extractStack` с флагами |
| Sorting 10 | `GH.findSomethingSortCore` (:543), `AISortingGoto:60`, `AISortingPlace:49,58`, `AIHomeTakeSorting:51,106` | «в получателе уже лежит такой предмет» (затравка) и забор из дома |
| Fill/Empty/Use с Order | `getColorsMatching` (E:517-535) | цвета слотов, чьи образцы «равны» предмету |
| Gather 2 | — | флаги **не читаются** (`AIItemPickup` их не использует), хотя переключатели показаны |

## Очередь Liquid (`AILiquidGather:168-183, 255-300`)

С Entropy у ядра Liquid строится очередь соединённых жидких блоков (флуд по 26 соседям от размеченного блока, радиус `range²`,
только блоки той же жидкости, годные к откачке), **отсортированных от самых далёких** (`Collections.reverseOrder()`), и голем
забирает по одному блоку из очереди вместо только размеченного; очередь пересчитывается, когда пуста.

## Решения порта (до реализации)

- Метаданные 1.7 в 1.21 сплющены в отдельные предметы: «игнорировать повреждение» — игнорировать компонент `DAMAGE`,
  «игнорировать NBT» — игнорировать все компоненты (сравнивать только предмет); без повреждений/компонентов у обоих — как есть.
- «Ore dictionary» — теги: материальный тег `c:` (`c:ingots/iron`, `c:ores/…`, `c:dusts/…`, `c:gems/…`, `c:nuggets/…`, `c:storage_blocks/…`,
  `c:raw_materials/…`, `c:rods/…`, `c:plates/…`, `c:gears/…`, `c:dyes/…`, `c:crops/…`, `c:seeds/…`) или один из `minecraft:logs`,
  `minecraft:planks`, `minecraft:saplings`, `minecraft:leaves`, `minecraft:wooden_slabs`, `minecraft:wooden_stairs`. Отклонение:
  симметрично, без «первого ore-имени» (порядок регистрации в 1.21 не определён); широкие корневые теги `c:ingots` и нематериальные
  `c:tools/pickaxe`, `c:armors/…`, `c:foods/…` не считаются (первый прогон GameTest показал, что `c:tools/pickaxe` содержит все кирки и
  уравнял бы железную с алмазной — в оригинале у инструментов ore-имён нет).
- Переключатели — свой ключ данных (как маска Guard), оригинальный `toggles` не переиспользуется.

## Реализация (Fabric/common, 19.10.2026)

Статус маркеров: **implemented / built / game-tested — да; seen — нет** (три флажка меню, подписи, расположение; клиент не запускался; NeoForge не трогался).
**Не перенесено:** очередь Liquid у Entropy (флуд соединённых источников, самые далёкие первыми) — остаётся следующей частью группы Entropy.

- `GolemItemMatch` — чистые правила: флаги `TAGS=1`, `IGNORE_DAMAGE=2`, `IGNORE_COMPONENTS=4`, кнопки меню `55..57` (оригинальные id), `appliesTo` (Fill, Empty, Gather, Use, Sorting),
  `configurable` (ядро + Entropy ≥ 1), `effective` (Empty/Use при Entropy всегда добавляют `TAGS`), `matches(stock, wanted, flags)`, `isGroupTag`.
  «Ore dictionary» — материальные `c:`-теги (корни `ingots`, `nuggets`, `ores`, `dusts`, `gems`, `storage_blocks`, `raw_materials`, `rods`, `plates`, `gears`, `dyes`, `crops`, `seeds`)
  и деревянные семейства `minecraft:` (`logs`, `planks`, `saplings`, `leaves`, `wooden_slabs`, `wooden_stairs`).
- `GolemData.itemMatch` (12-й компонент, совместимый 11-аргументный конструктор): JSON `item_match` (0..7, опускается при 0, строгая целочисленность), сеть — бит `0x40`
  последнего байта объявляет один байт переключателей после строки декорации (0 и значения вне трёх бит — ошибка декодера), конструктор записи отказывает в переключателях
  без Entropy и на ядре, где их нет.
- `GolemHomeInventory`: перегрузки `firstExtractable/countVisible/hasSeedAndRoom(..., match)`; `roomFor` остаётся строгим (вместить может только тот же стек).
- `EntityGolemBase`: `getItemMatch()`, `canSwitchItemMatch()`, `setItemMatch/toggleItemMatch`, `itemMatchFlags()` (с расширением для Empty/Use); `takeFromInventory` берёт **стек со склада**, а не образец
  (как в оригинале), `colorsMatching` сравнивает по сырым переключателям, `useItemAllowed` — по эффективным; NBT `ItemMatch` (байт, пишется только при ≠ 0; значение без Entropy, вне трёх бит, чужого типа
  или на ядре без переключателей — «неподдерживаемые данные», голем инертен); плейсер/колокольчик переносят значение через `configuredData`.
- `InventoryGolemGoals`: все пробы Fill/Empty/Sorting получают эффективные флаги; домашний кандидат Sorting намеренно остаётся строгим (он берёт стек из самого же слота).
- `ContainerGolem`: `DATA = 21`, индексы 19/20 (значение и «есть ли переключатели»), кнопки 55–57 с серверным отказом для чужих ядер и голема без Entropy; `GuiGolem`: три флажка
  (позиции оригинала: Sorting `(66, 36+10n)`, остальные `(180, 24+10n)`), подписи en/ru.
- Исправления чужих тестов по раскладке байта: `GolemGuardTargetsTest`, `GolemAdvancedTest`, `GolemDecorationsTest` (бит 64 теперь легален, повреждены только биты ≥ 128).

**Находки при проверке.** (1) GameTest с настоящими тегами показал ошибку правила групп: первая версия считала любым групповым тегом всякий `c:` с `/`, и `c:tools/pickaxe` (все кирки) уравнивал железную кирку с алмазной;
правило сужено до материальных корней, в JUnit добавлены отрицательные примеры, в GameTest — проверка «железная ≠ алмазная». JUnit этого не видит: в его Bootstrap теги не привязаны.
(2) Первая раскладка десяти линий в ряд шириной 20 блоков была стёрта стартом соседнего GameTest (он зачищает блоки вокруг своей структуры) уже на 1-м тике; линии стоят этажами над одним пятачком.

**Тесты.** `GolemItemMatchTest` (11 JUnit: кнопки, ядра, `effective`, группы тегов, точное/без урона/без компонентов, JSON/NBT/сеть, раскладка байтов, отказ без Entropy, равенство) и GameTest
`entropySwitchesChangeWhatRealGolemsFetchEmptyAndSort` (`GolemItemMatchRuntimeChecks`): настоящий игрок и меню (кнопки 55–57, поддельные 54/58/−55/155, отказы без Entropy и на Harvest), 11 ядер-скамеек,
цвета слотов при переключателях, NBT/плейсер/устаревшие и поддельные сохранения, затем **десять настоящих големов в пяти парах**, различающихся только проверяемым переключателем (или Entropy):
Fill+урон (забирает потёртые кирки, ровно две, не опустошает склад — счёт склада тоже нечёткий), Fill+компоненты (переименованный меч; «только урон» не даёт), Fill+теги (берёза вместо дуба),
Empty (Entropy расширяет дуб до любых досок без переключателей) и Sorting (затравка-дуб принимает берёзу). Отрицательные големы каждый тик не должны сдвинуть ни одного предмета.

**Мутации** (по одной, затем побайтное восстановление, sha256 сверен): 41 мутант. Пойманы 37: 17 чистых правил и проводных проверок (JUnit), правило тегов (только GameTest: в JUnit тегов нет) и 19 проводок (GameTest: поиск и счёт склада, пробы маршрута Fill/Empty/Sorting,

Use в игре, клиентский вид флажков и сеть с двумя игроками остаются открытыми.
