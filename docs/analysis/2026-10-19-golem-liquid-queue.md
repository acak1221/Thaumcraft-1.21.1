# Очередь Liquid (Decanting) у Entropy — контракт оригинала, 19.10.2026

Источник: оригинал TC4 4.2.3.5 (локальная декомпиляция CFR вне репозитория), `AILiquidGather` (`updateTask` :75-163, `rebuildQueue`, `getConnectedFluidBlocks`,
`validFluidBlock`, `SourceBlock`); в порте — `LiquidGolemGoals` (цели, маркеры, цикл забора) и `EntityGolemBase` (авторитет добычи).

## Что делает оригинал

1. Без Entropy голем откачивает **размеченный** блок жидкости, стоя рядом с маркером (расстояние маркера до голема < 2 блоков).
2. С Entropy (`getUpgradeAmount(5) > 0`) для каждого размеченного блока `loc` рядом с големом ведётся очередь `queue[loc]`. Если очереди нет или она пуста —
   `rebuildQueue(loc, fluid)`: `pumpDist = getRange()²`, обход в глубину от `loc` по **26 соседям** (циклы `a, b, c` от −1 до +1, середина пропускается); соседа
   пропускают, если его квадрат расстояния до `loc` больше `pumpDist` или блок — не та жидкость (текучая и стоячая вода считаются одной). Подходящий блок
   добавляется в очередь, если он «годен» (`validFluidBlock`: жидкость той же, источник метаданных 0), и обход заходит в него, даже если он не источник. Очередь
   сортируется `Collections.sort(.., reverseOrder())` — **самые далёкие от маркера первыми**, равные расстояния сохраняют порядок обнаружения.
3. Каждый «импульс» голем снимает из головы очереди (до первого годного блока) один блок и откачивает **его**, а не маркер; цель добычи может быть до `range`
   блоков от маркера. Условие `FluidRegistry.getFluid(..).getBlock() != bi` проверяет блок **маркера** — пока он стоит, голем работает.
4. Сам маркер достижим из соседей, поэтому он в очереди (с расстоянием 0) и снимается **последним**; когда очередь опустела, строится новая, и, если вокруг ничего нет, голем
   откачивает сам маркер.
5. Один импульс — одно ведро; после каждого забора счётчик `count` сбрасывается (следующий через ~10 тиков), цикл заканчивается без результата за 20 тиков.

## Ошибки оригинала (проверено чтением кода)

- Блок добавляется в очередь при **каждом** посещении соседа до проверки кэша обхода: источник, у которого k посещённых соседей, стоит в очереди до k раз; маркер — до 26 раз.
- Цикл `do { взять голову } while (осталось > 0 && !годен)` всегда берёт хотя бы одну запись. Если последняя запись уже стала не источником (дубликат снятого блока), `i, j, k`
  остаются указывать на неё, и ветка воды для метаданных `== 0` (у воздуха они нулевые) **выдаёт 1000 мБ из ничего** и «снимает» воздух. Это воспроизводимый дефект
  авторитета (дублирование воды), его перенос не нужен.
- Обход рекурсивный (`StackOverflowError` — не `Exception`, не ловится).

## Решения порта (до реализации)

- Чистое правило `GolemLiquidQueue.build(origin, range, connects, source)`: тот же порядок обхода в глубину (итеративно, явный стек), 26 соседей, `inRange` по `(float) distSqr ≤ range²`,
  устойчивая сортировка по убыванию расстояния. **Отклонения:** каждая клетка в очереди один раз (позиции дубликатов не имели смысла, кроме дефекта выше); обход останавливается после
  `MAX_VISITED = 65536` клеток, чтобы огромное озеро не повесило серверный тик.
- «Той же жидкости» для прохода — любой `minecraft:water` (источник или текучая); в очередь попадает только обычная вода-источник без блок-сущности (`LiquidGolemGoals.sourceWater`).
- Поведение голема: очередь по размеченному блоку, перестраивается, когда пуста; записи **перепроверяются** при каждом импульсе (всё ещё обычный источник и в пределах `getRange()` с учётом
  текущих улучшений); пустая очередь — цель сам маркер. Очереди чистятся для снятых маркеров и при сбросе голема.
- Авторитет добычи (`EntityGolemBase`): прежний узкий путь «размеченный блок рядом» остаётся, к нему добавлен «якорь» — размеченный блок рядом с големом (<2 блока), сам ещё обычный источник; цель
  может быть другим источником только при Entropy и в пределах `getRange()` от якоря. Разрешения защиты, события `BREAK`, кэш чанков и учёт воды работают на настоящей цели.
- Только вода (в порте других жидкостей нет), только ядро Liquid и только Fabric.
