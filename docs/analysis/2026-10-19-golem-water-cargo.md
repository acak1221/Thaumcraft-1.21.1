## Finite stock API

- Public immutable **`record GolemWaterCargo(int amountMb)`**, constructor range **0…5000** inclusive; `EMPTY` is zero, `BUCKET=1000`, reserved **`PLACER_KEY="WaterCargo"`**. Integers include partial mB remainders; this is actual stock representation, not an item bucket, ghost quantity, GolemData field or display snapshot. Constructing/serializing a value does not prove ownership or authorize output.
- **`static int capacityForMaterial(int material)`** uses `EnumGolemType.isSupported` then **`floor(sqrt(type.carry))*1000`**: material0/1/2/3/5/6/7 → **1000/2000/2000/2000/4000/5000/5000mB**. Unsupported values, including Flesh4 despite enum presence, throw. Ordinary only; no upgrade-derived capacity is invented.
- **`void validateMaterial(int material)`** rejects unsupported material or amount above its actual ordinary capacity, without modifying anything. The global constructor/parser limit is not a substitute for this material-specific check. Future root placement must separately validate actual item/material/core association and safe stock ownership/admission.
- **`CompoundTag save()`** creates a fresh exact compound **`{Version:1(int), Fluid:"minecraft:water"(string), AmountMb:int}`**, including explicit zero. **`static GolemWaterCargo parse(CompoundTag)`** requires exactly those keys/types, version1, exact water identity and amount0…5000. Missing/extra keys, numeric coercion (byte/long/float instead of int), malformed data, unknown versions/fluids and out-of-range amounts throw `IllegalArgumentException`; null arguments are refused. No input tag is mutated, normalized, clamped or deleted; caller retains the original raw payload on failure.

## Reserved native placer payload, not connected recall

- **`static GolemWaterCargo readPlacer(ItemStack)`** reads `DataComponents.CUSTOM_DATA` only. Complete absence **or an empty CustomData compound** returns `EMPTY`, matching the existing placer's absence equivalence. Otherwise the sole permitted top-level key is **WaterCargo**, with compound type and the exact nested payload above. Explicit valid zero parses normally; invalid/unknown data never falls back to EMPTY. Other CUSTOM_DATA keys are refused even if WaterCargo is absent or valid. No other native component, name, item count or source stack is changed.
- **`void writeToPlacer(ItemStack)`** requires a nonempty stack, edits a **copy** of CUSTOM_DATA and changes only WaterCargo. Unrelated keys/values and other native components are preserved. Existing wrong-type/invalid/future WaterCargo is parsed and refused **before mutation**, including an EMPTY write; it is never overwritten as a cleanup operation. Positive stock writes its fresh compound; zero removes only WaterCargo, removing CUSTOM_DATA itself only when no keys remain. Empty component and absent component remain semantically equivalent.
- Read/write asymmetry is deliberate: writer can preserve unrelated custom data without laundering it; such a stack **still fails readPlacer's strict unknown-key rule and existing placement**. Root must not interpret successful serialization as validation of unrelated data or use it to sanitize an otherwise rejected placer. Material/core/component association checks remain outside this independent class.
- **Current ItemGolemPlacer is unchanged and unconnected**: its `configuration` check (lines173–179 as reviewed) refuses **nonempty CUSTOM_DATA**, including a valid WaterCargo compound; an empty component alone is accepted. Therefore this helper does **not** make water-bearing recall items placeable or implement working Decanting5 recall. Root must explicitly integrate retained stock with normal recall, entity NBT, placement/admission and material/core checks as part of the complete functional unit.
