# Native four-slot accessories, Vis amulets and runic baubles

Gameplay source is original TC4 4.2.3.5: ItemAmuletVis, ItemBaubleBlanks, ItemRingRunic, ItemAmuletRunic, ItemGirdleRunic, EventHandlerRunic, WandManager75–120, TileVisRelay95–104, ConfigRecipes348–356/407–409 and ConfigAspects435. This is a native public API adaptation in thaumcraft.api.baubles; it does not load or claim binary compatibility with the old Forge Baubles dependency.

Player owns exactly four attached native slots:0amulet,1ring,2ring,3belt. Native ContainerAccessories uses vanilla carried stack/stateId/click processing, actual slot category/equip/unequip gates, stacklimit1 and quick-move. The open packet contains no item, slot, quantity, charge or player id. Server accepts only the current alive nonspectator with own inventory menu and empty carried stack. Native window packets carry the actual component-bearing items. A separate fixed-four-stack S2C snapshot keeps the owner's closed-menu discounts current; no C2S item state is accepted. New GUI uses native inventory art/layout; no inspected client screenshot exists.

Fresh-world player NBT stores complete native ItemStacks under thaumcraft:accessories. Atomic decode rejects invalid/duplicate/out-of-range slots, wrong categories, non-one counts and malformed items; original raw input is saved inactive for diagnosis instead of duplication or silent loss. Greater amulet research gates insertion only, not reloading an already worn stack. Native Player.dropEquipment returns exactly the four actual stacks on non-keepInventory death with original eye position,40 pickup delay and original randomized horizontal motion/.2Y. Slots relinquish ownership before spawning. Native PlayerList clone transfers remaining ownership to the respawned player and empties the old attachment, covering kept inventory and dimension replacement. Original optional separate creative/survival .baub files are not migrated; original default splitSurvivalCreative=false matches one native player inventory. Fresh worlds only.

Every fifth native player update transfers min(5,room,stored) per primal to the actual held wand, then charges from the original relay association. Greater equip requires VISAMULET; lesser is unrestricted. Original relay association scans block AABB+5 every twentieth relay node update, replaces an older association only when this relay is at least as close, and consumption requires squared center distance<26. Transient cache contains UUID/dimension/position/instance token, no strong Player/Level/BE references; quit/server stop clear it. Stale/replaced/unloaded associations cannot become donors.

Original consumeVisFromInventory tests independent full amulet payers in slots0→3 BEFORE main-inventory wands35→0. Amulets pay the unmodified raw bill; a short amulet loses nothing and does not split with another payer. Repair and Runic reuse that shared method. Relay source debit and amulet credit run inside a narrow prepared native worn-update frame: exact current player/slot/stack/component/relay is checked before debit, and one-use executor credit commits BEFORE route pulse callbacks. A callback can physically detach the paid item without losing or duplicating its committed component, and cannot replay its grant.

Runic discovers four armor plus four accessory slots. Charged rings subtract500ms each from configured recharge interval, retaining the original zero/negative boundary instead of adding a floor. Depletion order is kinetic (explosion1.5+.5*count, no fire/block damage,20s cooldown), healing (regeneration240ticks, amplifier=count,20s cooldown), emergency (min(max,8*count),60s cooldown). Emergency runs after the previous upgrades and suppresses the ordinary global wait if it refills positive charge. Timers are transient; existing native charge persistence and global dirty/recharge-delay behavior remain shared with the armor implementation. Modern native explosion/damage/regen engine details are forced APIs, not bitwise1.7 entity physics.
