## Question

Does a real held thaumometer scan produce wrong aspect knowledge, lose the
discovery, or mutate the wrong player? Test the five requested target kinds and
separate proven runtime failures from source-only reasoning.

## Oracle observations

Read the private original `ScanManager`, `ResearchManager`,
`ThaumcraftCraftingManager` and `ThaumcraftApiHelper`. Independently ran `javap
-p -c` on the immutable original JAR: `getBonusTags` returns the result of
`ThaumcraftApiHelper.cullTags` at bytecode offsets 1285–1288, with no final
`capAspects` call. SHA-256 checked against the documented original.

Native `ObjectAspectResolver.get` nevertheless calls `cull(cap(result))` and its
comment falsely attributes that final cap to the original. This can suppress
scan research points when positive contained essentia overlaps base tags.
The test declares a legal public-addon base tag of air4 on the real jar item,
then scans a physical jar containing air64: oracle reward68, native baseline64.
The fixture also changes contents from32 to64 midway through the same physical
scan to prove the reward samples completion-time values rather than a stale
start snapshot.

Two assumptions in the requested hypothesis are not original mechanics:
ordinary scans do not grant warp, and node modifiers do not change scan aspects.
The new tests assert the original behavior instead of adding either mechanic.
