## 1. `thaumcraft/api/wands/WandTriggerRegistry.java` — public trigger registry

### The original

* `oracle thaumcraft/api/wands/WandTriggerRegistry.java:25-32` — the trigger is keyed by the
  pair `Arrays.asList(block, meta)`.
* `oracle …:38-45` — `hasTrigger(Block, int)` answers **true** when the exact registration
  `Arrays.asList(block, meta)` **or** the wildcard registration `Arrays.asList(block, -1)`
  exists, over every mod id.
* `oracle …:47-53` — `hasTrigger(Block, int, String)` is the same answer for one mod id and
  returns `false` for an unknown mod id.
* `oracle …:55-86` — `performTrigger` looks the exact registration up first and the wildcard
  registration second; the first successful trigger wins.

### The port before this wave

* `common/src/main/java/thaumcraft/api/wands/WandTriggerRegistry.java:81-92` — `hasTrigger(BlockState,
  String)` only asked for the **exact state** key, so a trigger that was registered for a whole
  block was invisible to the public answer although `performTrigger` (line 99-109) did accept it.
  The public answer and the public dispatch disagreed.
* The original's `hasTrigger(Block, int, String)` and both `performTrigger(..., Block, int[, String])`
  signatures did not exist at all — an add-on compiled against 1.7.10 could not call them.

### The fix

* `hasTrigger(BlockState, String)` now consults the exact state key **and** the whole block key,
  exactly like `performTrigger` does. The public answer and the public dispatch now agree.
* `hasTrigger(Block, int, String)` was restored.
* `performTrigger(..., Block, int)` and `performTrigger(..., Block, int, String)` were restored.
  **Forced 1.21.1 change:** 1.21.1 has no block metadata, so the metadata argument survives in the
  signature, is ignored, and the exact state of the block is its default state. The wildcard
  registration of the whole block stays the fallback, exactly as in the original.

### The test

`common/src/test/java/thaumcraft/api/WandTriggerRegistryApiTest.java` (authored, not executed):
the answer and the dispatch agree for a block keyed registration, an unregistered block has no
trigger, and the restored block-and-metadata dispatch reaches its registration.

## 2. `thaumcraft/api/aura/AuraHelper.java` — the drain of the retained 1.12 surface

### The original

This class is **not** a TC4 class: it is absent from the oracle
(`ls /home/cyberfox-kali/work/thaumcraft-4.2.3.5-oracle/thaumcraft/api/` has no `aura` directory).
The reference is therefore the retained 1.12 source of this repository:

* `src/main/java/thaumcraft/api/aura/AuraHelper.java:20-22` — `drainVis` delegates to
  `AuraHandler.drainVis(world, pos, amount, simulate)`.
* `src/main/java/thaumcraft/common/world/aura/AuraHandler.java:27-33` — that method floors the
  request and delegates to `VisNetHandler.drainVis(world, x, y, z, requested, simulate)`.
* `src/main/java/thaumcraft/api/visnet/VisNetHandler.java:92-139` — the drain walks the **primal
  aspects** of every **root source** that is in range of the position and takes
  `min(remaining, source.getAvailableVis(aspect))` of each.

So the one working method of the retained surface drained the **vis network at the position**.

### The port before this wave

* `common/src/main/java/thaumcraft/api/aura/AuraHelper.java:48-60` — `drainVis` walked the
  **essence of the aura node at the position** instead. An add-on that expected the network wide
  drain saw a different result.

### The fix

* `AuraHelper.drainVis(Level, BlockPos, int, boolean)` now delegates to
  `VisNetHandler.drainVis(Level, BlockPos, int, boolean)`.
* `common/src/main/java/thaumcraft/api/visnet/VisNetHandler.java` — a new public
  `drainVis(Level, BlockPos, int, boolean)` walks the primal aspects in the original order of
  `Aspect.getPrimalAspects()` (the original `Aspect.aspects` is a `LinkedHashMap`, oracle
  `thaumcraft/api/aspects/Aspect.java:25,148-156`, so the registration order is the original
  order) and bounds every aspect by what is still requested. A dry run uses the new read-only
  `availableVis` probe; a real run reuses the existing per-aspect network drain unchanged.
* `common/src/main/java/thaumcraft/api/visnet/TileVisNode.java` — a new `availableFromSource`
  hook; `common/src/main/java/thaumcraft/common/tiles/TileNodeEnergized.java` answers it with the
  same stock that its debit would take, under the same guards.

**Forced 1.21.1 change:** the amount of the retained surface was a `float`; the native surface
uses an `int`. The `getVis`/`addVis` accessors of the retained surface threw
`UnsupportedOperationException` (they addressed a per-chunk aura that TC4 does not have); the
native ones read and write the aura node at the position, which is a superset of the original
behaviour and is documented as such.

### The test

`common/src/test/java/thaumcraft/api/AuraHelperDrainTest.java` (authored, not executed): the
guards, the order of the six primal aspects and the bounded plan of the aspect-less drain.

## 3. `thaumcraft/api/research/ResearchItem.java` — the executable triggers

### The original

* `oracle thaumcraft/api/research/ResearchItem.java:19-44` — the nine flags, the parents, the
  siblings, the **executable** `itemTriggers`, `entityTriggers` and `aspectTriggers` and the pages.
* `oracle thaumcraft/api/research/ResearchItem.java:144-167` — the setters and the getters of the
  three trigger kinds. An add-on reads exactly those.
* `oracle thaumcraft/common/config/ConfigAspects.java:107-109` and
  `oracle thaumcraft/common/config/ConfigResearch.java` — the corpus registers the aspect
  triggers (`setAspectTriggers`) and the item triggers (`setItemTriggers`) of its entries.

### The port before this wave

* `common/src/main/java/thaumcraft/api/research/ResearchItem.java:81-109` — the public view of a
  corpus entry copied the flags, the parents, the siblings, the entity triggers and the pages, but
  **not** the aspect triggers and **not** the item triggers: `getAspectTriggers()` and
  `getItemTriggers()` answered `null` for every corpus entry.
* The triggers of the corpus live in the common layer
  (`common/src/main/java/thaumcraft/common/lib/research/ResearchTriggerBindings.java`), so the
  public accessors could not reach them.

### The fix

* `ResearchItem.of(ResearchDefinition)` now copies `definition.aspectTriggers()` into
  `aspectTriggers` (as the original `Aspect` objects) and leaves `entityTriggers` at `null`
  when the entry has none — exactly like the original.
* `ResearchItem.getItemTriggers()` resolves the native identity of the bound items of the entry
  through `ResearchTriggerBindings.boundStacks` and answers `null` when the entry has no item
  trigger, exactly like the original. The resolution is done on every call, because the native
  identity of a mod item only exists after the mod registered it.
* `common/src/main/java/thaumcraft/common/lib/research/ResearchTriggerBindings.java` — the
  bindings of the item triggers became ordered lists (the original order of the
  `setItemTriggers` call) and the four tiny clothing entries, whose original trigger is the wool
  block, are now bound as well.
* `common/src/main/java/thaumcraft/api/research/ResearchPage.java:127-165` — the eight
  `legacy_expression` pages of the corpus are mapped to the page kind of the original expression
  (arcane, crucible, normal, infusion or smelting) instead of the blanket `IMAGE`.

**Remaining gap (documented):** the public `icon_item` and `icon_resource` of a corpus entry are
still `null`; the original icon of an entry is an arbitrary Java expression
(`new ItemStack(ConfigBlocks.blockMetalDevice, 1, 3)`), and the port restores it at draw time
through the client side `ResearchIconDisplay`. The `BANNERS` and `OUTERREV` item triggers are
also still unbound: their original trigger is a block metadata that 1.21.1 flattened into a
distinct block id.

### The test

`common/src/test/java/thaumcraft/api/ResearchItemTriggerTest.java` (authored, not executed): the
corpus is reachable through the public registry, the executable aspect and item triggers are
answered, an entry without a trigger answers `null`, every page of every entry is reachable and
the page kind of the eight array pages is the original one.

## 4. `thaumcraft/common/lib/events/EventHandlerEntity.java` — the death aspect orbs

### The original

* `oracle thaumcraft/common/lib/events/EventHandlerEntity.java:508-516` (the CFR 0.152
  decompilation; the 1.7.10 readable source of the same code is
  `OpenTC4 …/lib/events/EventHandlerEntity.java:534-546`):

  ```java
  } else if (!event.entityLiving.worldObj.isRemote && EntityUtils.getRecentlyHit(event.entityLiving) > 0) {
     AspectList aspectsCompound = ScanManager.generateEntityAspects((Entity)event.entityLiving);
     if (aspectsCompound != null && aspectsCompound.size() > 0) {
        AspectList aspects = ResearchManager.reduceToPrimals(aspectsCompound);
        for (Aspect aspect : aspects.getAspects()) {
           if (!event.entityLiving.worldObj.field_73012_v.nextBoolean()) continue;
           EntityAspectOrb orb = new EntityAspectOrb(event.entityLiving.worldObj, ..., aspect,
                   1 + event.entityLiving.worldObj.field_73012_v.nextInt(aspects.getAmount(aspect)));
           event.entityLiving.worldObj.spawnEntityInWorld(orb);
        }
     }
  }
  ```

  So: one **primal** aspect of the dead mob per roll, a fifty percent roll per aspect, and a
  value of `1 + nextInt(amount of that aspect)`. Both rolls come from the **world** random
  (`field_73012_v` is `World.rand`).
* `oracle thaumcraft/common/entities/EntityAspectOrb.java:57-68` — the scatter of the orb uses
  `Math.random()`, not the world random, so the orb itself never moves the world stream.
* `oracle thaumcraft/common/lib/research/ResearchManager.java:466-495` — the reduction to the
  primals; the native `AspectList.reduceToPrimals(false)` reproduces it in the same order (the
  original `AspectList.aspects` is a `LinkedHashMap`, oracle
  `thaumcraft/api/aspects/AspectList.java:23`).
* The **order** of the death: the Forge 1.7.10 patch of `EntityLivingBase.onDeath` is
  `if (ForgeHooks.onLivingDeath(this, p_70645_1_)) return;` **at the top of the method**, and the
  drop block (`dropFewItems` and the `LivingDropsEvent`) comes after it. The native
  `EntityEvent.LIVING_DEATH` of Architectury is injected at `@At("HEAD")` of the 1.21.1
  `LivingEntity.die`, and `dropAllDeathLoot` is called inside `die` after that point. **The two
  orders are the same**, so the two rolls of an aspect happen before the loot of the same death.
* The **gate**: vanilla 1.7.10 sets `EntityLivingBase.recentlyHit` only when a player hurts the
  mob (the Forge patch of `attackEntityFrom`), and the Forge `LivingDropsEvent.recentlyHit` is
  the same flag. The native equivalent of that flag is the 1.21.1 `lastHurtByPlayerTime`, which
  the native taint swarm (`EntityTaintSwarm.java:200`), the native fire bat
  (`EntityFireBat.java:195`) and the native golem (`EntityGolemBase.java:1401`) already use for
  the original `EntityUtils.setRecentlyHit` calls.

### The port before this wave

* There was **no** death aspect orb at all: a mob never dropped vis.
* Wave 1 wrote the rule and the hook (`67ba2edf`) and reverted them (`8bc39488`), because the
  orbs move the world random stream of a death and the native GameTests of several lanes lock
  that stream. The reverted hook also used `invulnerableTime` (the 1.21.1 damage cooldown, set
  by **every** damage) as the "recently hit" gate, which is not the original flag.

### The fix

* `common/src/main/java/thaumcraft/common/lib/entities/DeathAspectOrbRules.java` — the pure
  rule: the reduction to the primals, one boolean per primal and, for every true roll, the value
  `1 + nextInt(amount)`. **Forced 1.21.1 change:** the original would call `nextInt(0)` for a
  primal without an amount and crash the death; the native rule skips such a primal.
* `common/src/main/java/thaumcraft/common/entities/DeathAspectOrbDrop.java` — the hook. The gate
  is the original one: the taint poison branch wins, and the orbs need the recently-hit flag
  (`lastHurtByPlayerTime > 0`), which is the native equivalent of the 1.7 `recentlyHit`. The two
  rolls come from the **world** random (`server.getRandom()`).
* `common/src/main/java/thaumcraft/common/Thaumcraft.java:108` — the registration.

### The proof that the world stream really is shifted

The port consumed **no** world random at a death, the original consumes `2` rolls per primal
aspect of the dead mob before the loot. The stream of the port therefore differed from the
stream of the original for **every player-attributed death of an aspect bearing mob**, and the
GameTests that lock that stream had to be re-derived.

The 1.21.1 `RandomSource` is bit for bit the `java.util.Random` LCG
(`BitRandomSource.nextInt`, `nextBoolean`, `nextFloat` and `nextLong` are the vanilla ones, and
`LegacyRandomSource.next` is `seed = seed * 25214903917 + 11` over 48 bits), so the new
expectations were derived with an exact simulation of that generator. The simulation reproduces
the seeds that the existing GameTests already use (`allFleshSeed(3) = 7`,
`allFleshSeed(12) = 200`, `goldSeed() = 3`, `fireSeed(false,false) = 1`,
`zapSeed(false,true) = 1`, `seedForTame() = 0`), which proves the simulation.

The three GameTests that lock the world stream of such a death were re-derived:

* `common/src/gameTest/java/thaumcraft/common/testing/TaintSporeRuntimeChecks.java` — the three
  scripted deaths now begin with the **refused** orb rolls of the dead mob (four booleans for
  the Spore and for the Swarmer, five for the tiny spider, from
  `oracle thaumcraft/common/config/ConfigAspects.java:92-94`). Every roll refuses, so no orb is
  dropped and the original loot draws of the fixture stay exactly where they were.
* `common/src/gameTest/java/thaumcraft/common/testing/BrainyZombieRuntimeChecks.java` — the
  player-attributed Giant death now starts behind the six orb draws of the Giant
  (`aer 6, ordo 6, aqua 12, terra 14, perditio 7, ignis 3`, from oracle `ConfigAspects:89`),
  and the seed helper derives the new seed (1484 instead of 200). The environmental deaths keep
  the old helper, because the original drops no orb for them.
* `common/src/gameTest/java/thaumcraft/common/testing/PechRuntimeChecks.java` — the death of the
  Pech now starts behind the six orb draws of the Pech of type zero
  (`aer 8, ordo 8, aqua 14, terra 14, ignis 6, perditio 10`, from oracle `ConfigAspects:84`),
  and the seed helper derives the new seed (8 instead of 3).

The other GameTests that kill a mob were checked and need no change: the taint swarm re-seeds the
world random after the death, the tainted animal always drops exactly one material
(`TaintAnimalRules.taintedDrop`, the chicken is a single `nextInt(4)`), the taintacle accepts
either of its two drops, the cultist and the eldritch beasts use the **entity** random for their
loot, and the fire bat and the wisp die of an environmental damage.

### The test

`common/src/test/java/thaumcraft/common/lib/entities/DeathAspectOrbRulesTest.java` (authored, not
executed): the reduced primals of the original brainy zombie, one orb per primal aspect, the

  `setNodeModifier(thaumcraft.api.nodes.NodeModifier)` and translates them by name (the two enums

* `common/src/main/java/thaumcraft/api/nodes/NodeAdapter.java` — the two setters write the node

`TileNodeEnergizedRenderer.java`, `common/src/main/java/thaumcraft/common/lib/world/NodeEcology.java`
and `NodeGeneration.java` — the client lane and the worldgen lane, which this wave does not own.
The identity of the node is a UUID instead of the original `dim:x:y:z` string, and the scanning
subsystem uses that identity.

### The test

`common/src/test/java/thaumcraft/api/NodeTypeContractTest.java` (authored, not executed): the six
