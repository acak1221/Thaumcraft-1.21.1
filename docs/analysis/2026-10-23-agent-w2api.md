## 1. `thaumcraft/common/lib/events/EventHandlerEntity.java` — the death aspect orbs

**This was the named open item of wave 1 and the most valuable one.**

### The original

* `oracle thaumcraft/common/lib/events/EventHandlerEntity.java:508-516` — the `LivingDeathEvent`
  handler has two branches: a mob that carries the taint poison and that is not a tainted mob
  is replaced by its tainted twin, and **every other mob that was recently hit drops one aspect
  orb per primal aspect of its scanned aspects**:

  ```java
  } else if (!event.entityLiving.worldObj.isRemote && EntityUtils.getRecentlyHit(event.entityLiving) > 0
          && (aspectsCompound = ScanManager.generateEntityAspects(event.entityLiving)) != null
          && aspectsCompound.size() > 0) {
      AspectList aspects = ResearchManager.reduceToPrimals(aspectsCompound);
      for (Aspect aspect : aspects.getAspects()) {
          if (!event.entityLiving.worldObj.rand.nextBoolean()) continue;
          EntityAspectOrb orb = new EntityAspectOrb(world, x, y, z, aspect,
                  1 + event.entityLiving.worldObj.rand.nextInt(aspects.getAmount(aspect)));
          world.spawnEntityInWorld(orb);
      }
  }
  ```

  So: **one roll of the WORLD random per primal aspect**, a fifty percent chance of an orb, and
  a value of `1 + nextInt(amount of that aspect)` from the same world random.
* `oracle thaumcraft/common/entities/EntityAspectOrb.java:57-68` — the scatter of the orb
  (yaw and the three motion components) uses `Math.random()`, **not** the world random.
* `oracle thaumcraft/common/lib/research/ResearchManager.java:466-495` — the reduction to the
  primals, reproduced by the native `AspectList.reduceToPrimals(false)`.
* `oracle thaumcraft/common/lib/utils/EntityUtils.java:141-156` — the "recently hit" flag is the
  1.7.10 `EntityLivingBase.recentlyHit` (`field_70718_bc`). The Forge 1.7.10 patch of
  `EntityLivingBase.attackEntityFrom` sets it to 100 **only when the attacker is a player**.

### The order of the world random — PROVEN, not assumed

Wave 1 reverted its implementation because it "shifts the world-random stream of every mob
death". The shift is real, and it is the original's own behaviour:

* the **Forge 1.7.10 patch of `net/minecraft/entity/EntityLivingBase.java`** starts
  `onDeath` with `ForgeHooks.onLivingDeath(this, source)` — the `LivingDeathEvent` of the
  original — and only *after* that captures the drops (`captureDrops = true;` …) and fires
  `ForgeHooks.onLivingDrops(...)` — the `LivingDropsEvent` of the original, whose handler
  (`oracle EventHandlerEntity:449-478`) draws the zombie brain, the villager resource and the
  champion reward **from the world random**. The hunks are `@@ -883,6 +888,7 @@`,
  `@@ -908,6 +914,10 @@` and `@@ -923,6 +933,16 @@` of that patch.
* the **native** `dev.architectury.event.events.common.EntityEvent.LIVING_DEATH` is injected by
  `dev.architectury.mixin.fabric.LivingDeathInvoker` (architectury-fabric 13.0.11) at
  `@At("HEAD")` of the 1.21.1 `LivingEntity.die`, and the native `dropAllDeathLoot(level, source)`
  is called *inside* that same method (bytecode offset 156 of `LivingEntity.die`).

⇒ the native orbs are drawn **before** the native death loot, exactly like the original, and the
world stream of a death that a player caused is shifted by the orb rolls in both.

### The fix

* `common/src/main/java/thaumcraft/common/lib/entities/DeathAspectOrbRules.java` — the pure
  rule: `AspectList.reduceToPrimals(false)`, then per primal `nextBoolean()` and, only for a
  true roll, `1 + nextInt(amount)`. No world, no level, no registry — unit testable.
* `common/src/main/java/thaumcraft/common/entities/DeathAspectOrbDrop.java` — the death hook on
  the Architectury `LIVING_DEATH`:
  * the taint branch of the original is honoured (a mob with the flux taint that is not a
    tainted mob never reaches the orb branch),
  * the gate is the original one: `lastHurtByPlayerTime > 0` (the native form of the 1.7.10
    `recentlyHit`, which only a player attack sets),
  * the scanned aspects come from the same bindings as the original scan
    (`EntityAspectBindings.describe`),
  * the orb is published through the same guarded factory as the node emission
    (`EntityAspectOrb.unspawned`), and the scatter uses `Math.random()` like the original.
* `common/src/main/java/thaumcraft/common/Thaumcraft.java:108` — the registration.

**Forced 1.21.1 changes:** the 1.7.10 `recentlyHit` flag became `lastHurtByPlayerTime`; the
`EntityAspectOrb` constructor became a guarded factory that refuses an invalid orb; the
original would have crashed the death with `nextInt(0)` for a primal without an amount, the
native rule skips such a primal instead (documented in `DeathAspectOrbRules`).

## 5. `thaumcraft/common/CommonProxy.java` — the original proxy (analysed)

The original proxy is a Forge loader artefact. Its add-on surface is

* the three state accessors (`getPlayerKnowledge`, `getResearchManager`, the wand manager) and
  the five knowledge accessors that return the **global** maps of every player
  (`oracle CommonProxy:52-77`),
* the numeric server GUI element factory with the container ids 0, 1, 2, 3, 5, 8, 9, 10, 13, 15,
  16, 17, 18, 19, 20 (`oracle CommonProxy:93-155`),
* about sixty client effect entry points (`oracle CommonProxy:158-327`).

The port has **no proxy at all** (`common/src/main/java/thaumcraft/common/Thaumcraft.java` is a
static bootstrap), and none of the three groups can be reproduced as they were:

* the player knowledge is **per player** in the persistent data of the player
  (`native common/src/main/java/thaumcraft/common/lib/research/PlayerKnowledge.java`), so there
  is no global map of every player to hand out;
* the research of a player is reached through the native research layer (the original
  `ResearchManager` is decomposed into `ResearchCatalog`, `ResearchCategories`, `ResearchClues`,
  `PlayerKnowledge` and `ScanManager`), so `getResearchManager()` would need a compatibility
  facade with the thirty public methods of the original class;
* the GUI ids are replaced by the native `MenuProvider` of every block entity, and the client
  effects live in the dedicated client effect classes.

**Decision for the leader:** a `Thaumcraft.proxy` compatibility facade (with the knowledge
accessors and the GUI id contract) is possible, but it needs a global knowledge registry that
the port deliberately does not have. The unit stays `partial` with that blocker.
