## 1. The brain bob — the test was wrong

### The original

* oracle `thaumcraft/client/renderers/tile/TileJarRenderer.java:155-175` (`renderBrain`):

  ```java
  float bob = MathHelper.func_76126_a((float)((float)Minecraft.func_71410_x().field_71439_g.field_70173_aa / 14.0f)) * 0.03f + 0.03f;
  ```

  `field_71439_g` is `thePlayer`, `field_70173_aa` is `Entity.ticksExisted`.
  The argument is a **float** division `ticksExisted / 14.0f` and the whole expression is
  **float** arithmetic.
* `MathHelper.func_76126_a` is the 1.7.10 vanilla sine **lookup table**, not a `Math.sin`.
  I decompiled the 1.7.10 client jar (`net/minecraft/util/MathHelper` is the obfuscated
  `qh.class`, the only class of that jar that holds the constant `10430.378`):

  ```java
  private static float[] a = new float[65536];
  public static final float a(float f) { return a[(int)(f * 10430.378f) & 0xFFFF]; }   // func_76126_a = sin
  public static final float b(float f) { return a[(int)(f * 10430.378f + 16384.0f) & 0xFFFF]; } // func_76134_b = cos
  static { for (int i = 0; i < 65536; ++i) qh.a[i] = (float)Math.sin((double)i * Math.PI * 2.0 / 65536.0); }
  ```

  The oracle's own copy of the vanilla table is `thaumcraft/codechicken/lib/math/MathHelper.java:15-23`
  (`SIN_TABLE[(int)((float)d * 10430.378f) & 0xFFFF]`), the same table in a `double` flavour.
* The 1.21.1 `net.minecraft.util.Mth.sin(float)` is **the same table** (read out of the
  remapped 1.21.1 jar: `SIN[(int)(value * 10430.378F) & 65535]` with
  `SIN[i] = (float)Math.sin((double)i * Math.PI * 2.0 / 65536.0)`), so the native
  `Mth.sin` reproduces `MathHelper.func_76126_a` **bit for bit**.

### The port

* `common/src/main/java/thaumcraft/client/renderers/tile/TileJarBrainRenderer.java:77-79`

  ```java
  public static float bob(int ticksSinceLevel) {
      return Mth.sin(ticksSinceLevel / BOB_PERIOD) * BOB_AMPLITUDE + BOB_AMPLITUDE;
  }
  ```

  `int / 14.0f` is the float division of the original, `Mth.sin` is the original's table and
  the rest is float arithmetic: **the port is the original**.

* The failing value of the wave-3 report is the proof: `0.029962609` is the original's own
  float at tick 44 (I recomputed the 1.7.10 table: `SIN[(int)(3.1428571f * 10430.378f) & 0xFFFF]`
  = `-0.00126442091f`, `* 0.03f + 0.03f` = `0.029962609f`).

### What the original really does (and what the test claimed)

The sine of the original is negative in the second half of every period, so the bob runs
from **zero** to `0.06`:

| tick | the original's bob |
|---|---|
| 0 | `0.03` |
| 7 | `0.04438229` |
| 14 | `0.05524354` |
| 22 | `0.059999995` (the maximum) |
| 28 | `0.057279825` |
| 44 | `0.029962609` (the value of the failure report) |
| 66 | `5.029142E-8` (the minimum, the brain is at the bottom of its swing) |
| 88 | `0.03007478` |

Over the 512 ticks of the old test, **248 of them are below 0.03**. The old assertion

```java
assertTrue(bob >= .03F - 1.0E-6F && bob <= .06F + 1.0E-6F, "the original brain bob stays between 0.03 and 0.06, not " + bob);
```

is therefore false for the original, and the test failed on the first tick below 0.03
(tick 44 → `0.029962609`).

### The fix (test only)

`common/src/test/java/thaumcraft/client/renderers/tile/JarRendererParityTest.java:38-55`
now asserts the exact floats of the original table (0.03 / 0.04438229 / 0.05524354 /
0.059999995 / 0.029962609 / 0.057279825 / 5.029142E-8) and the true range `[0, 0.06]`.
The production file got a comment that records *why* it is `Mth.sin` and not a `Math.sin`
(a `Math.sin` would differ from the original by up to `2.8e-6`).

## 2. The brain turn — the test was wrong

### The original

* oracle `thaumcraft/client/renderers/tile/TileJarRenderer.java:160-166`:

  ```java
  for (f2 = te.rota - te.rotb; f2 >= 3.141593f; f2 -= 6.283185f) { }
  while (f2 < -3.141593f) { f2 += 6.283185f; }
  float f3 = te.rotb + f2 * f;
  GL11.glRotatef((float)(f3 * 180.0f / 3.141593f), (float)0.0f, (float)1.0f, (float)0.0f);
  ```

  The difference `te.rota - te.rotb` is wrapped into `[-3.141593, 3.141593)` with the
  constants **`3.141593f` and `6.283185f`** (not `(float) Math.PI`), and the drawn angle is
  `f3 = te.rotb + f2 * f` — the **absolute** interpolated angle of the brain, not the
  difference.
* The same constants and the same wrap are in the tile that feeds the renderer, oracle
  `thaumcraft/common/tiles/TileJarBrain.java:87-104` (`rota`, `rotb`, the difference loop
  and `rota += f * 0.04f`).

### The port

* `common/src/main/java/thaumcraft/client/renderers/tile/TileJarBrainRenderer.java:85-90`
  (`turn`) is a line by line copy of the original, constants included.
* `common/src/main/java/thaumcraft/common/tiles/TileJarBrain.java:144-151` is a line by line
  copy of the original's client tick (`3.141593F` / `6.283185F`, the difference loop and
  `rota += delta * .04F`).

**Both are the original.**

### What the test claimed

```java
assertEquals(0F, TileJarBrainRenderer.turn(1F, 1F, .5F), 1.0E-6F);
```

The test expected the *difference* of the two angles, but the original returns the
*interpolated absolute angle*. With `rota == rotb == 1` the brain does not move at all: the
difference is `0`, and the drawn angle is `rotb + 0 * 0.5` = **1.0 radian**. The port
returned `1.0`, the test wanted `0.0` — that is the "expected: `<0.0>` but was: `<1.0>`".

### The fix (test only)

`common/src/test/java/thaumcraft/client/renderers/tile/JarRendererParityTest.java:57-69`
now asserts `turn(1, 1, .5) == 1`, `turn(2, 1, .5) == 1.5`, the wrap of the difference
`5 - 1 = 4` into `4 - 6.283185` (`-1.283185`) and the wrap of `-5 - 1 = -6` into
`-6 + 6.283185` (`1.283185`). The expected value uses the original's own constant
`6.283185F` (the old test used `2 * 3.141593F`, which is *not* the original's constant and
was only inside the 1e-4 tolerance by luck).

## 3. The arcane furnace shell — the test was wrong

### The original

* oracle `thaumcraft/common/items/wands/WandManager.java:349-373` (`fitArcaneFurnace`):

  ```java

  Block bn = Blocks.field_150385_bj;     // nether bricks
  Block bf = Blocks.field_150411_aY;     // iron bars
  Block bl = Blocks.field_150353_l;      // lava
  Block[][][] blueprint = new Block[][][]{
      {{bn, bo, bn}, {bo, Blocks.field_150350_a, bo}, {bn, bo, bn}},
      {{bn, bo, bn}, {bo, bl, bo}, {bn, bo, bn}},
      {{bn, bo, bn}, {bo, bo, bo}, {bn, bo, bo}}};
  ```

  (`Blocks.field_150350_a` is the air block: the same file uses it as the "empty" cell of
  the shell and `ConfigRecipes.java:89` lists the research page of the construct with the
  `empty` slot in the same place.)
  The cell of the layer `yy` is read at `y - yy + 2` (`WandManager.java:359`), so the
  blueprint is written from the **top** layer down:

  | layer | original |
  |---|---|
  | 0, the top layer | nether bricks in the corners, obsidian on the edges, **air** in the middle |
  | 1, the middle layer | nether bricks in the corners, obsidian on the edges, **lava** in the middle |
  | 2, the bottom layer | nether bricks in the corners, **obsidian** everywhere else |
* The research page of the construct, oracle `thaumcraft/common/config/ConfigRecipes.java:89`,
  lists the same 27 cells: layer 0 = `nb ob nb / ob empty ob / nb ob nb`, layer 1 =
  `nb ob nb / ob lava iron_bars / nb ob nb`, layer 2 = `nb ob nb / ob ob ob / nb ob nb`.
  The iron bar is the one cell of the middle layer that the original accepts as an
  alternative to the obsidian edge (`WandManager.java:363-368`).
* The three trigger blocks of the event two are oracle `ConfigRecipes.java:90-92`:
  the obsidian, the nether bricks and the iron bars.

### The port

* `common/src/main/java/thaumcraft/common/lib/ArcaneFurnaceFormation.java:96-108`
  (`expected(layer, dx, dz)`) returns exactly that blueprint, layer 0 = top, and
  `fits(...)` reads the layer `layer` at `base.offset(dx, 2 - layer, dz)` — the original's
  `y - yy + 2`.
* `isTriggerBlock(...)` (`:84-86`) is the original's three trigger blocks.

**The production is the original.**

### What the test claimed

The old test looped over the three layers and, for the middle cell of **every** layer,
asserted the top layer's rule:

```java
if (dx == 1 && dz == 1) {
    assertSame(Blocks.AIR, ArcaneFurnaceFormation.expected(layer, dx, dz), "the middle of the top layer of the original shell is empty");
    ...
}
```

Layer 0 passed (air), layer 1 failed (lava) — that is the reported
"expected: `<Block{minecraft:air}>` but was: `<Block{minecraft:lava}>`".

### The fix (test only)

`common/src/test/java/thaumcraft/wands/ArcaneFurnaceFormationTest.java:29-56` now checks
the corners and the edges of the three layers and then the middle of each layer on its own:
air (top), lava (middle), obsidian (bottom). No assertion was weakened: the shell is
still checked in all 27 cells, and the `Blocks.LAVA` form of the wave-3 survival change
(1.21.1 has one liquid block, the flowing lava is `Blocks.LAVA` with a level) stays.

## 7. A mistake of mine that the leader has to clean up

While committing the report I used `git add -A` and my private Gradle home
(`.gradle-fix3/`, 1.1 GB) was not in `.gitignore` yet, so the commit **af442838** of this
branch accidentally carried the whole Gradle cache. The leader's merge script picked that
commit up at 11:47, so **`refs/heads/work` contains af442838 and its tree carries a 1.1 GB
`.gradle-fix3/` directory**.

* This branch is already clean: the commit was rewritten, the branch is now
  `8fb49c8f -> 370f02fd -> 991d9016` and `.gitignore` has `.gradle-fix3/`.
* The leader has to drop the directory from the tree of `work` (the history keeps the
  blobs until it is rewritten):

  ```
  cd /home/cyberfox-kali/Thaumcraft-1.21.1
  git rm -r --cached .gradle-fix3 && rm -rf .gradle-fix3
  git commit -m "chore: drop the accidental Gradle home of the w3fix3 agent"
  ```

  and to reclaim the 1.1 GB of the history, a filter plus a prune
  (`git filter-repo --path .gradle-fix3 --invert-paths` or the equivalent
  `git filter-branch --index-filter 'git rm -r --cached --ignore-unmatch .gradle-fix3'`)
  followed by `git reflog expire --expire=now --all && git gc --prune=now`.
* The three test fixes are in **370f02fd**, which is already an ancestor of `work`, so the
  next test run of the leader already has them. Only the report, the ledger evidence and
  the `.gitignore` entry still need the merge of this branch.
