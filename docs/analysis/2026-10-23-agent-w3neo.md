## 0. What the previous wave left, and what this wave corrects

The wave-2 report (`docs/analysis/2026-10-23-agent-neoforge.md`) left three client
features and four GameTest scenarios open. **One of its statements about NeoForge
is wrong and is corrected here**, because it is the reason the first gap could not
be closed with the mechanism the report named:

> wave-2, §6.1: "**NeoForge 21.1: there is no fluid render handler event.** The whole
> NeoForge client fluid API is `IClientFluidTypeExtensions` (tint, still/flowing/overlay
> texture, camera overlay, fog) and `FluidType` (the server side properties). None of
> them can change the *geometry* of a fluid."

**That is false.** `IClientFluidTypeExtensions` has a drawing hook:

* `net/neoforged/neoforge/client/extensions/common/IClientFluidTypeExtensions.java:347`
  — `default boolean renderFluid(FluidState fluidState, BlockAndTintGetter getter,
  BlockPos pos, VertexConsumer vertexConsumer, BlockState blockState)`, documented as
  "Called to allow rendering custom quads for a fluid during chunk meshing. You may
  replace the fluid rendering entirely, or return false to allow vanilla's fluid
  rendering to also run."
* It is called from the **NeoForge patch** of the vanilla fluid draw path,
  `patches/net/minecraft/client/renderer/block/BlockRenderDispatcher.java.patch`
  (the `renderLiquid` method):
  `if (net.neoforged.neoforge.client.extensions.common.IClientFluidTypeExtensions.of(p_234368_).renderFluid(p_234368_, p_234365_, p_234364_, p_234366_, p_234367_)) return;`

So the NeoForge-native hook for the clean water render **exists**. It is nevertheless
**unusable for the TC4 purifying fluid**, and the reason is a registration rule, not a
missing API:

* The hook belongs to the `FluidType`. The purifying fluid **must** share the vanilla
  water type on NeoForge: `net/neoforged/neoforge/common/extensions/ILivingEntityExtension:23`
  and `net/neoforged/neoforge/fluids/FluidType:360` compare the type by **identity**
  against `NeoForgeMod.WATER_TYPE`, so an own type would make the purifying fluid
  invisible to every water rule of the engine (this is exactly why
  `neoforge/src/main/java/thaumcraft/neoforge/mixin/NeoForgeFluidPureMixin.java:34`
  publishes the water type).
* The water type **already owns** a client extension: NeoForge registers it in
  `net/neoforged/neoforge/client/ClientNeoForgeMod.java:98`
  (`event.registerFluidType(new IClientFluidTypeExtensions() { … }, NeoForgeMod.WATER_TYPE.value())`).
* `net/neoforged/neoforge/client/extensions/common/ClientExtensionsManager.java:42`
  refuses a second registration for the same type:
  `throw new IllegalStateException("Duplicate client extensions registration for %s …")`.

⇒ A second registration for the water type would **crash the client at startup**, so
the native hook cannot carry the purifying fluid. The only remaining place is the
vanilla draw path itself, which is where the mixin of this wave sits.

## 1. Part B — the three GameTest probes and the research table scenario

### 1.1 The gap

The three excavation scenarios of the shared harness reflected into the **Fabric API**
class `net.fabricmc.fabric.api.event.player.PlayerBlockBreakEvents`, which does not
exist on NeoForge:

| Scenario | Shared probe | Reflection site |
|---|---|---|
| `excavationextraremovalfailureaccounting` | `ExcavationRemovalFailureRuntimeChecks.AfterProbe` | `…/ExcavationRemovalFailureRuntimeChecks.java:221` (before this wave) |
| `excavationharvestpreservesprotectionlootandcontainers` | `ExcavationHarvestRuntimeChecks.FabricProbe` | `…/ExcavationHarvestRuntimeChecks.java:397` (before this wave) |
| `excavationupgradetreasureandenlarge` | `ExcavationUpgradeRuntimeChecks.AfterProbe` | `…/ExcavationUpgradeRuntimeChecks.java:199` (before this wave) |

On NeoForge each of them failed with
`IllegalStateException("Native removal AFTER observer unavailable")` /
`"Fabric native event probe unavailable"` / `"Actual native AFTER probe unavailable"`.

### 1.2 The fix — a loader neutral phase observer

The shared harness now never names a loader class. A new shared interface owns the
three phases:

* `common/src/gameTest/java/thaumcraft/common/testing/NativeBreakPhases.java` — the
  phases `BEFORE`, `CANCELED`, `AFTER`, the `Listener` callbacks and the `Holder` the
  loader bootstrap fills.

**Fabric** (`fabric/src/gameTest/java/thaumcraft/fabric/testing/FabricBreakPhases.java`)
keeps the *exact* previous behaviour: it decorates the actual invoker of the three
`PlayerBlockBreakEvents` and restores the exact previous invoker on close. The
existing listeners still run first and the BEFORE phase may still refuse the break.
The Fabric bootstrap installs it
(`fabric/src/gameTest/java/thaumcraft/fabric/testing/ThaumcraftGameTestBootstrap.java:18`).

**NeoForge** (`neoforge/src/gameTest/java/thaumcraft/neoforge/testing/NeoForgeBreakPhases.java`)
uses its own native graph:

* **BEFORE / CANCELED** — the cancellable
  `net.neoforged.neoforge.event.level.BlockEvent.BreakEvent`, observed at
  `EventPriority.LOWEST`. The NeoForge javadoc of that event
  (`net/neoforged/neoforge/event/level/BlockEvent.java:56-66`) names the three
  conditions under which it fires already cancelled: `Player#blockActionRestricted`,
  a `GameMasterBlock` without the permission and `Item#canAttackBlock`. Those are
  exactly the conditions that keep the **Fabric** BEFORE from running, because the
  Fabric BEFORE is injected directly before the `Block.playerWillDestroy` call of
  `ServerPlayerGameMode.destroyBlock` (the refmap of the Fabric API,
  `client-fabric-rendering-v1-refmap.json` / `fabric-events-interaction-v0-refmap.json`,
  maps `renderArmor`/`tryBreakBlock` onto `method_4169`/`method_14266`).
  The observer therefore **skips** the BEFORE phase for an event that is already
  cancelled, exactly like Fabric.
  The lowest priority also sees the final cancellation state, because the
  Architectury `BlockEvent.BREAK` of this mod runs at `EventPriority.HIGH`
  (`net/neoforged/neoforge/event/forge/EventHandlerImplCommon.java:429-435`, it calls
  `event.setCanceled(true)` when the Architectury result is false).
* **AFTER** — the **real** removal. NeoForge 21.1 routes the removal through its own
  private helper, so the AFTER phase observes the return value of that helper:
  `neoforge/src/gameTest/java/thaumcraft/neoforge/testing/mixin/NeoForgeBreakPhaseMixin.java`
  injects at the `RETURN` of
  `ServerPlayerGameMode.removeBlock(BlockPos, BlockState, boolean)` and only reports a
  removal when the helper returned `true`. That is the same witness the Fabric AFTER
  event has (the Fabric API injects it directly before the `Block.destroy` call of
  `destroyBlock`, which the NeoForge patch moved into the very same helper).

**Mixin targets, verified against the NeoForge-patched bytecode.** The descriptors
were read with `javap -p -s` from the NeoForge-patched archive
`…/neoforge-21.1.259-minecraft-merged-de6471c7bf-…jar` (the patched Minecraft of the
NeoForge 21.1.259 userdev jar), **not** from the vanilla classes:

```
$ javap -p -s net.minecraft.server.level.ServerPlayerGameMode
  private boolean removeBlock(net.minecraft.core.BlockPos, net.minecraft.world.level.block.state.BlockState, boolean);
    descriptor: (Lnet/minecraft/core/BlockPos;Lnet/minecraft/world/level/block/state/BlockState;Z)Z
```

The mixin uses exactly that descriptor and declares `require = 1`.

### 1.3 The research table scenario

`tablebreakevacuateseachhalfonce` waits for the drop delivery of the shared
`DeferredItemDrops` at the Architectury `TickEvent.SERVER_LEVEL_POST`. That tick is
**loader neutral** (Architectury implements it on NeoForge as well), so the scenario
needed no NeoForge specific tick. Its failure was a *consequence* of the three broken
probes above: the shared fixture tears the research table down through the very same
native `destroyBlock` path, so the scenario could not finish its teardown while the
probe threw. With the probe in place the scenario reaches its own assertion.

## 2. Part A — the three client features

### 2.1 The clean water render of the purifying fluid

* **NeoForge-native mechanism.** `IClientFluidTypeExtensions#renderFluid` exists (see
  §0) but is unreachable for the purifying fluid, because the fluid must share the
  vanilla water `FluidType` and the water type already owns its client extension.
  ⇒ the NeoForge-native position of the draw is the NeoForge-patched
  `BlockRenderDispatcher#renderLiquid`, which is exactly the method NeoForge patched
  to add its own hook.
* **The fix.** The original geometry now lives in the **shared** module
  `common/src/main/java/thaumcraft/client/renderers/fluid/PureFluidRender.java`:
  the source height `0.875`, the flowing height `quanta / 8 * 0.875`, the four corner
  averages with the Forge rule `PureFlowRules.renderAverage`, the `0.001` offset, the
  UV rotation of a flowing cell, the side shades `0.8` (north, south) and `0.6`
  (west, east), the bottom shade `0.5` and the section-relative vertex coordinates.
  The Fabric handler became a thin adapter
  (`fabric/src/main/java/thaumcraft/fabric/client/FabricFluidPureRenderHandler.java:45`)
  and the NeoForge half is the client mixin
  `neoforge/src/main/java/thaumcraft/neoforge/mixin/client/NeoForgePureFluidMixin.java:65`.
  Both loaders therefore draw the *same* geometry, from the *same* code.
* **Mixin targets, verified against the NeoForge-patched bytecode:**
  ```
  $ javap -p -s net.minecraft.client.renderer.block.BlockRenderDispatcher
    public void renderLiquid(net.minecraft.core.BlockPos, net.minecraft.world.level.BlockAndTintGetter,
        com.mojang.blaze3d.vertex.VertexConsumer, net.minecraft.world.level.block.state.BlockState,
        net.minecraft.world.level.material.FluidState);
      descriptor: (Lnet/minecraft/core/BlockPos;Lnet/minecraft/world/level/BlockAndTintGetter;Lcom/mojang/blaze3d/vertex/VertexConsumer;Lnet/minecraft/world/level/block/state/BlockState;Lnet/minecraft/world/level/material/FluidState;)V
    public void onResourceManagerReload(net.minecraft.server.packs.resources.ResourceManager);
      descriptor: (Lnet/minecraft/server/packs/resources/ResourceManager;)V
  ```
  Both are used verbatim; the mixin declares `require = 1`.
  The client mixin lives in its own config
  `neoforge/src/main/resources/thaumcraft-neoforge-client.mixins.json` with a
  `"client"` list, so the dedicated server never loads it.

### 2.2 The original TC4 gear models (the void robe, the fortress armour, the hover harness)

* **NeoForge-native mechanism.** The NeoForge patch of
  `net/minecraft/client/renderer/entity/layers/HumanoidArmorLayer.java` adds
  `protected Model getArmorModelHook(T entity, ItemStack itemStack, EquipmentSlot slot,
  A model)`, and `net/neoforged/neoforge/client/ClientHooks.java:322` forwards it to
  `IClientItemExtensions.getGenericArmorModel`; the sheet comes from
  `ClientHooks.getArmorTexture` (same file, line 260) → `ArmorItem.getArmorTexture`.
* **Why the native hook alone is not enough.** The hook can only return a `Model`.
  The original hover harness renderer
  (`common/src/main/java/thaumcraft/client/renderers/models/gear/HarnessArmorRenderer.java`)
  draws the chest cube **and** the retained 124 triangle OBJ pack on the back with its
  own unlit render type; an OBJ pack has no model expression.
* **The fix.** The NeoForge half draws the pieces from its own armour layer with the
  **very same shared renderers the Fabric loader uses**:
  `common/src/main/java/thaumcraft/client/ThaumcraftGearModelsClient.java:181`
  (`renderGearItem`) dispatches to `renderRobe`, `renderFortressArmor` and
  `HarnessArmorRenderer.render`; the Fabric loader keeps its three
  `ArmorRenderer.register` calls and the NeoForge mixin
  `neoforge/src/main/java/thaumcraft/neoforge/mixin/client/NeoForgeGearArmorMixin.java:48`
  calls the same dispatcher. The two loaders therefore draw the gear from the same
  code with the same render type; the cultist plate and the cultist leader armour are
  **not** drawn by the dispatcher, because the Fabric loader never registered them
  (they keep the native armour layer on both loaders).
* **Mixin target, verified against the NeoForge-patched bytecode:**
  ```
  $ javap -p -s net.minecraft.client.renderer.entity.layers.HumanoidArmorLayer
    private void renderArmorPiece(com.mojang.blaze3d.vertex.PoseStack, net.minecraft.client.renderer.MultiBufferSource,
        T, net.minecraft.world.entity.EquipmentSlot, int, A);
      descriptor: (Lcom/mojang/blaze3d/vertex/PoseStack;Lnet/minecraft/client/renderer/MultiBufferSource;Lnet/minecraft/world/entity/LivingEntity;Lnet/minecraft/world/entity/EquipmentSlot;ILnet/minecraft/client/model/HumanoidModel;)V
  ```
  This is the same method the Fabric API intercepts: the Fabric mixin
  `net/fabricmc/fabric/mixin/client/rendering/ArmorFeatureRendererMixin` injects into
  `renderArmor`, which the refmap of the Fabric API resolves to
  `Lnet/minecraft/class_970;method_4169(…)V` — the six argument `renderArmorPiece`.
  `require = 1` is declared.

### 2.3 A latent NeoForge client crash that this wave found and fixed

The shared client mixin `thaumcraft.common.mixin.client.RobeArmorLayerMixin` redirected
the call `ItemStack.is(TagKey)` inside `HumanoidArmorLayer#renderArmorPiece`. **The
NeoForge patch of that class has no such call**: the patch replaced

```java
-  int i = itemstack.is(ItemTags.DYEABLE) ? FastColor.ARGB32.opaque(DyedItemColor.getOrDefault(itemstack, -6265536)) : -1;
+  int fallbackColor = extensions.getDefaultDyeColor(itemstack);
```

(NeoForge 21.1.259 userdev jar, `patches/net/minecraft/client/renderer/entity/layers/HumanoidArmorLayer.java.patch`).
A `@Redirect` whose target does not exist **fails the whole mixin application**, and the
shared config has `"injectors": {"defaultRequire": 1}` — so a real NeoForge client
would have **crashed at startup**. The dedicated server never applies the shared
`"client"` mixin list, which is why the NeoForge GameTest suite never saw it.

The fix splits the behaviour by loader:

* **Fabric** — `fabric/src/main/java/thaumcraft/fabric/mixin/client/FabricRobeArmorLayerMixin.java`
  keeps the redirect, now in a Fabric own client mixin config
  (`fabric/src/main/resources/thaumcraft-fabric-client.mixins.json`).
* **NeoForge** — the native equivalent: the client item extension
  `IClientItemExtensions#getDefaultDyeColor` publishes the same colour for the robe
  items (`neoforge/src/main/java/thaumcraft/neoforge/client/ThaumcraftNeoForgeClient.java:107`),
  and the colour itself is the shared `ItemRobeArmor.armorTint(stack)`
  (`common/src/main/java/thaumcraft/common/items/armor/ItemRobeArmor.java:68`), which is
  the vanilla `FastColor.ARGB32.opaque(DyedItemColor.getOrDefault(stack, -6265536))`.

### 2.4 The `taint_fibres` model — still open

The NeoForge-native hook of the wave-2 report is
`net/neoforged/neoforge/client/event/ModelEvent.java:48` (`ModifyBakingResult`), which
hands the mod the map of the baked models and a sprite lookup. It cannot express the
TC4 model, because the model is **neighbour dependent** and the vanilla
`BakedModel.getQuads` has no world access:

* the six fibre planes are drawn only on the sides whose neighbour is not a solid
  family member (oracle `thaumcraft/client/renderers/block/BlockTaintFibreRenderer.java:38-56`),
* the crossed stalks of the metadata one and two are drawn only when the cell below is
  sturdy (oracle, same file, lines 57-95), with the original deterministic grass offset
  `(x * 3129871) ^ (z * 116129781) ^ y` (shared `TaintSpreadRules.grassOffset`).

⇒ the NeoForge half needs a mixin into the native block renderer, where the world and
the position are available. The exact place is known and verified:

* `net.minecraft.client.renderer.block.ModelBlockRenderer#tesselateWithoutAO` (and its
  AO sibling) — the NeoForge-patched class
  (`patches/net/minecraft/client/renderer/block/model/ModelBlockRenderer.java.patch`)
  calls the **NeoForge extended** `BakedModel.getQuads(BlockState, Direction,
  RandomSource, ModelData, RenderType)`, so a replacement model on NeoForge must
  implement the five argument signature, not the vanilla four argument one.
* The injection point that carries the world and the position is the `HEAD` of
  `tesselateWithoutAO(BlockAndTintGetter, BakedModel, BlockState, BlockPos, PoseStack,
  VertexConsumer, boolean, RandomSource, long, int, ModelData, RenderType)`.

**This wave did not implement it.** The reason is the one the wave-2 report named and
it is still exact: the client cannot be started and inspected in this environment, and
a wrong winding, a wrong UV or a wrong lightmap in a custom block model is a
**visible** regression. The NeoForge half of this model would have to be built from
scratch (the neighbour dependent planes, the glow overlays at `0.98` with the lightmap
coordinate 200, the crossed stalks with the original grass offset and the four
surfaces of the old `renderCrossedSquares`) and none of it can be checked here. The
parity test keeps the gap tracked
(`neoforge/src/test/java/thaumcraft/neoforge/NeoForgeLoaderParityTest.java`,
`theKnownNeoForgeClientGapsAreTheDocumentedOnes`).

## 5. The acceptance criteria for the leader's NeoForge client run

**The visual result of every client change of this wave is UNVERIFIED.** The client
cannot be started in this worktree, so the leader has to confirm the following on a
real NeoForge client:

1. **Clean water render.** A pool of the purifying fluid next to a pool of water must
   show the TC4 surface height (a source cell is 7/8 of a block high, a flowing cell
   `quanta/8` of that), the TC4 side shading (north/south 0.8, west/east 0.6) and the
   TC4 bottom. The fluid must **not** be drawn with the vanilla water corners, and the
   surface must not be at the vanilla 8/8 height.
2. **Void robe.** A player wearing the void robe hood/robe/leggings must show the
   original TC4 robe model (the original 128x64 sheet, the original slot visibility:
   the head for the hood, the body and the arms for the robe, the legs for the
   leggings) and **not** the vanilla armour layer.
3. **Fortress armour.** A player wearing the Thaumium Fortress helm/chestplate/leggings
   must show the original TC4 fortress model with its own sheet and its own ornaments
   (the number of worn pieces, the infused mask, the goggles).
4. **Hover harness.** A player wearing the hover harness must show the TC4 chest cube
   **and** the retained OBJ back pack on the back, with the original sneak transform.
5. **Robe dye.** The dyed TC4 robe (the enchanted robe of the wearables) must show its
   dye colour in the worn view, exactly as on Fabric, and the wash in a water cauldron
   must still reset it to the default purple `0x6A3880`.
6. **No startup crash.** The NeoForge client must start at all: the shared
   `RobeArmorLayerMixin` redirect had no target in the NeoForge patched class and
   would have failed the mixin application (§2.3).
