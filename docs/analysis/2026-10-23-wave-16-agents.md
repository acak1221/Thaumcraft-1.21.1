# Wave of 2026-10-22 — 16 parallel agents, client acceptance, NeoForge parity

## Why this wave exists

The port of TC4 4.2.3.5 to Minecraft 1.21.1 was already deep: 1044 ledger units,
653 `parity_verified`, 315 `partial`, 58 `missing`, 310 required GameTest cases,
1828 JUnit tests, and a NeoForge module that had reached registration parity with
the Fabric bootstrap. Two things blocked the final acceptance:

1. **The client could not be started in the previous sandbox.** `docs/HANDOFF.md`
   recorded "GLX-контекст не создаётся ни с одним драйвером Mesa (100 fbconfig
   есть, контекста нет)" and therefore **no visual acceptance was performed and
   none was claimed**. 24 client units stayed `missing`/`partial` for exactly that
   reason, and the user asked for in-game bug and crash hunting.
2. **315 ledger units were still `partial`** — behaviour that was ported but never
   proven against the 1.7.10 original.

## What changed in this environment

The current machine has a working OpenGL 4.6 context (NVIDIA) on
`DISPLAY=localhost:10.0` (`glxinfo -B` reports a real renderer and 100+ fbconfigs
with a live context). The previous "no GLX context" finding belonged to a
different sandbox and does **not** hold here. The port already ships a complete
client harness (`:fabric:runClientSmoke`, `fabric/src/clientTest/...`, 27.5k
lines) that drives a real integrated world, captures named screenshots and
writes a machine-checked evidence contract, so client acceptance is now
reachable instead of permanently deferred.

Confirmed directly from the 1.21.1 bytecode
(`~/.gradle/caches/fabric-loom/minecraftMaven/.../minecraft-merged-1.21.1-loom*.jar`):
`BaseEntityBlock` overrides `getRenderShape(BlockState)` and returns
`RenderShape.INVISIBLE`, and `PistonBaseBlock` references
`BlockState.hasBlockEntity()`. Every port class that extends `BaseEntityBlock`
without overriding `getRenderShape()` is therefore invisible in the client, and
`hasBlockEntity` being true for the whole block stops the piston. 55 classes in
`common/src/main/java` extend `BaseEntityBlock`; the handoff's open
"cosmetic_solid*/eldritch* invisible" defect is the visible symptom of that
class-wide root cause.

### Wave 2 — result

Wave 2 closed the rest of the `partial` units and, more importantly, the **real**
defects that only a running game could show.

**Scope ledger: 841 -> 945 `parity_verified`** (the wave started at 653, so 292
units were closed); `partial` 189 -> 86; `missing` 10; `not_assessed` 3.

#### Defects that only a real client or a real server could find

* **Every TC4 world showed the player the "Worlds using Experimental Settings are
  not supported" dialog.** 1.21.1 computes the lifecycle of a saved world from its
  level stems: `WorldDimensions.bake` returns `experimental()` as soon as the
  world has more than the three vanilla stems, and `isVanillaLike` rejects every
  key that is not overworld/nether/end. The port registers the Outer Lands as a
  real level stem, so **every** world of the mod was experimental **for every
  player** — the generator is irrelevant. The proof is a byte-exact NBT probe that
  removed only that one entry: the client then opened the world with no dialog,
  while the same build asked on the four-dimension world. Fixed by
  `common/src/main/java/thaumcraft/common/mixin/Tc4LevelStemLifecycleMixin.java`,
  which makes the level stem registry report the stable lifecycle. The harness now
  **fails** the run if the dialog ever appears.
* **Picking up a TC4 special item killed the client.** 1.21.1 renders the item
  pickup animation with a *copy* of the picked entity, and `ItemEntity.copy()`
  keeps the entity **type** but not the entity **class** — a renderer typed to
  `EntitySpecialItem` therefore threw `ClassCastException`. Both item renderers
  now accept any `ItemEntity`, and the three item entity types that had **no**
  renderer at all were registered (1.21.1 has no fallback, so an unrendered
  entity type is an NPE the moment it is drawn).
* **The break notification fired twice on NeoForge** — the shared code fired
  Architectury's `BlockEvent.BREAK` *and* NeoForge's native `BlockEvent.BreakEvent`
  (which NeoForge forwards into it). The bridge now owns the notification.
* **The TC4 chest rows never reached any chest table on NeoForge** — the
  encode/decode round trip of a loot table is impossible (the dungeon table holds
  a *tag* set that is not bound while the loot data loads, and the row codec
  writes no `type`). The rows are now appended to the loaded pool itself, which
  is an exact match of the Fabric weighted list and draw order.
* **The taintacle tick crashed on NeoForge** — NeoForge 21.1 rewrites the damage
  pipeline (`hurt` pushes a `DamageContainer`, `actuallyHurt` peeks it) and the
  shared taintacle damage called `actuallyHurt` directly.
* **The purifying fluid was invisible to the water rules on NeoForge** — NeoForge
  compares the fluid *type* identity, not the tag.
* **The GameTest probes were never registered on NeoForge** — six scenarios turned
  green with that single registration.

#### The float sweep — 14 assertions that were not the original's values

One agent swept the 497 float/double assertions of the 274 new test files. 122
carried a tolerance (now none does), and **14 asserted a value the original never
produced** — the production code was wrong in seven of them:

* the tainted animals' flap speed, flap amplitude and fall damping: the original
  does that arithmetic in **double**, the port did it in float, and the two differ
  for 7 549 747 of the 16 777 216 inputs;
* the travelling trunk's lid angle: the oracle's `3.141593f`, not `(float) Math.PI`;
* the cultist's champion absorption: the oracle's **integer** division;
* the crimson portal's collision distance: **3.0**, not 9.0;
* the golem orb's speed clamp: the original narrows the motion to float first;
* the crucible's amount division.

#### The 1.7.10 piston — a premise that was wrong

The port's piston behaviour was audited against the **official Mojang 1.7.10
`client.jar`** and the official MCP mapping. 1.7.10 decided **per class, not per
metadata**: `BlockPistonBase#canPushBlock` ends with
`!(block instanceof ITileEntityProvider)`. A `BlockContainer` family was never
moved (any metadata); a plain `Block` family was moved for every metadata, and the
move **destroyed the tile** (1.7.10's `TileEntityPiston` carried only block and
metadata). The port now reproduces that exactly, with a common mixin on
`PistonBaseBlock#isPushable` whose target was verified in the real bytecode of
both the Fabric and the NeoForge jar.

#### The lesson the wave produced

Three separate waves had written the same wrong statement about a "creative
player is never found" rule, and it was only settled by reading the **original
1.7.10 source**: `if (!entityplayer1.isCreative() && entityplayer1.getDistanceSq(x, y, z) < d1)`.
The same held for the piston (per class, not per metadata) and for the
experimental-world dialog (per level stem, not per generator). **The oracle is the
only authority**, and the port's own comments are not evidence.
