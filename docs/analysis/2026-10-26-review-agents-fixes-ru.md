# Разбор с помощью субагентов: NeoForge, оверлей архитектора, производительность — 26.10.2026

По просьбе пользователя сбор информации делали субагенты (модель Sonnet, только чтение): обзор
горячих путей по мотивам оптимизаций TC4Tweaks, пробелы NeoForge относительно Fabric, дефекты
«порядка вызовов» NeoForge и план проверки ещё не осмотренных визуальных эффектов. Каждое
утверждение агентов перед правкой проверено по коду, байткоду NeoForge 21.1.259 или оригинала, а
дефекты — тестом, который падает до исправления.

## Исправлено

### 1. Жидкости на NeoForge (4 пробела, найдены агентом)

| Пробел | Было | Стало |
|---|---|---|
| Ведро очищающей жидкости — не контейнер жидкости на NeoForge | NeoForge оборачивает в `FluidBucketWrapper` только точный класс `BucketItem`; подкласс `ItemBucketPure` остался без `Capabilities.FluidHandler.ITEM`. Оригинал регистрировал пару «1000 mB жидкости ↔ ведро» в `FluidContainerRegistry` (`2026-10-20-purifying-fluid.md`) | `NeoForgeSpaStorage` регистрирует обёртку для `bucket_pure`; пустое ведро, наполненное из купели, становится ведром очищающей жидкости, а не ведром воды |
| `drain(int maxDrain, …)` тигля и купели | забирал весь бак, `maxDrain` игнорировался; `FluidUtil.tryFluidTransfer(…, 1000)` переливал больше ведра | ровно запрошенное (`FluidTank.drain` оригинала, `TileCrucible:395-397`) |
| Купель без стороны (`side == null`) | возможность не отдавалась | как на Fabric: нет только сверху |
| Обработчик тигля | двигал воду у снятого тигля и с чужого потока | только живой тигль на своей позиции и только на потоке сервера, как хранилище Fabric |

Новые GameTest только для NeoForge (`NeoForgeFluidCapabilityGameTests`, вне каталога, собираемого
из Fabric): `neoSpaCapabilityHonoursSidesAndDrainLimit`, `neoPureBucketIsAFluidContainer`,
`neoCrucibleCapabilityHonoursDrainLimitAndOwner`. На старом коде все три падают на ожидаемых
утверждениях (у купели первым ловится пропуск стороны `null`, проверка `maxDrain` за ним не
доходит; у тигля — симулированный слив на 250 mB).

### 2. Ускорение добычи в парящем поясе не работало на NeoForge

Оригинал: в полёте с включённым парением игрок копает со скоростью, как на земле (×5 снимает
штраф «в воздухе» ÷5). На NeoForge `Player.getDestroySpeed` — лишь обёртка, а ломание блока идёт
через `Player.getDigSpeed`, поэтому общий mixin не срабатывал. Байткод NeoForge подтверждает:
`BlockBehaviour.getDestroyProgress` → `getDigSpeed`, где ÷5 стоит перед
`EventHooks.getBreakSpeed`. Теперь Fabric — mixin `FabricHoverMiningMixin`, NeoForge — слушатель
`PlayerEvent.BreakSpeed` (то же событие Forge, что было в 1.7.10). Общий GameTest
`hoverHarnessMinesAtGroundSpeedWhileAirborne` на NeoForge до правки: `0.006666667` на земле против
`0.0013333334` в полёте.

### 3. Опыт за элдрич-блоки не выпадал на NeoForge

NeoForge всегда вызывает `spawnAfterBreak(…, false)` и начисляет опыт только через
`IBlockExtension.getExpDrop` (`CommonHooks.handleBlockDrops:545-548`). `BlockEldritch` давал опыт
только в `spawnAfterBreak`. Теперь, как у `BlockCustomOre`, есть публичный `getExpDrop` без
`@Override`: глифовый и рунный камень 1–4, порождатель крабов 6–10 (`BlockEldritch:197-205`).
Общий GameTest `eldritch_glyphed_stone_gives_its_experience` на NeoForge до правки: опыт `0`.

### 4. Оверлей фокуса-архитектора не был виден вообще

Агент заметил, что последняя партия оверлея не сбрасывается. Настоящий клиент Fabric показал
больше: оверлея не было вовсе (`images/2026-10-26-architect-before.png` — жезл с «Равноценным
обменом» и улучшением «архитектор», под прицелом только рамка блока). Байткод оригинала
`REHWandHandler.drawOverlayBlock` (javap над исходным JAR, вне репозитория):
`glDepthMask(false)`, `glDisable(GL_DEPTH_TEST)`, `glDisable(GL_CULL_FACE)`,
`glBlendFunc(SRC_ALPHA, ONE)`, границы `-0.001 … 1.001`, `GL_TEXTURE_ENV_MODE = GL_ADD`. Порт
рисовал куб ровно по граням блока с тестом глубины сущности — грани оказывались внутри рельефа.
Теперь своё состояние отрисовки с теми же параметрами, `GL_ADD` воспроизводит ядровой шейдер
`thaumcraft:architect_overlay` (цвет прибавляется к текстуре, альфы перемножаются), куб увеличен
на 0.001, партия сбрасывается сразу. Стрелки осей — то же состояние без `GL_ADD`
(`drawArchitectAxis`). Кадр после правки: `images/2026-10-26-architect-after.png` — оболочка
области 7×7 из рун защитного стекла и стрелки у якоря. Не воспроизведено: яркость 200 из
тесселятора оригинала (область рисуется на полной яркости) — записано в `KNOWN_DEVIATIONS` §7.2.
Шейдер зарегистрирован на обоих загрузчиках; в клиенте NeoForge оверлей не осматривался.

Там же осмотрен луч фокуса раскопок от первого лица: зелёная полоса от кончика жезла к цели,
блик в точке удара, трещины на блоке.

### 5. Производительность (обзор горячих путей)

Только изменения, не меняющие поведения:

- `VisNetHandler`: три защиты от рекурсии (`ThreadLocal`) снимались после каждого вызова, и
  каждый следующий вызов создавал новую `IdentityHashMap`; ретранслятор делает около десяти
  таких вызовов за тик. Наборы теперь остаются пустыми между вызовами.
- `ObjectAspectResolver`: каждое разрешение аспектов незарегистрированного предмета копировало все
  35 «сложных» привязок; теперь копируется одна нужная (`EarlyObjectAspectBindings.complexOf`).
- `ProgrammaticRecipes.crucibles`: упорядоченный список рецептов тигля пересобирался и
  сортировался на каждый предмет в тигле, на каждый рабочий тик таумотория и на каждый кадр его
  рендерера. Теперь он хранится для каждого `RecipeManager` (у клиента и сервера свои), пока не
  сменится набор рецептов (`/reload`, синхронизация) или список регистраций; поиск по id — по
  карте.
- `ResearchConditions`: регулярное выражение условий компилировалось на каждый узел книги на
  каждом кадре; теперь один `Pattern`.

Замеров нет: изменения убирают заведомо лишнюю работу, поведение проверено полными наборами
тестов. Отложено: кэш результатов `ObjectAspectResolver` (код намеренно ничего не кэширует между
вызовами; кэш требует надёжной инвалидации при регистрации тегов аддонами), пересчёт результата
магического верстака каждый тик, покадровые пересчёты карты исследований и спрайтов печи.

## Найдено, но не исправлено

- **Уведомление компараторам в `Level.removeBlockEntity` NeoForge** может синхронно грузить
  соседний чанк при снятии любого блока с блок-сущностью у края загруженной области (механизм
  проверен по байткоду, частота неизвестна). Для улучшенной печи это уже обойдено раньше;
  общий mixin NeoForge закрыл бы все случаи, но без падающего сценария не делался.
- **`emptyContents` с пятью аргументами** (NeoForge): ведро очищающей жидкости переопределяет
  только вариант с четырьмя. Сейчас недостижимо — поведение раздатчика для этого ведра не
  зарегистрировано ни на одном загрузчике; затронуты только сторонние моды, вызывающие новый
  вариант.
- Дропы мобов через `addFreshEntity` минуют захват дропов NeoForge (`LivingDropsEvent` других
  модов их не видит); на игру TC4 не влияет.
- Предметы, ставящие много блоков внутри захвата снимков NeoForge (жемчужина, элементальные
  лопата и мотыга и др.): отмена `EntityMultiPlaceEvent` откатит всё; падающего сценария нет.
